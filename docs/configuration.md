# Configuration

Three things shape what is mutated: a config file, the rules that select files, and comments in the source. A fourth file records accepted mutants.

## xcmutate.config.json

`run`, `list` and `instrument` read `xcmutate.config.json` from `--root`. For all three the default root is the git top-level directory of the current directory (outside a git repository, the current directory). `--config <path>` names another file. The file is meant to be committed. Every key is optional.

```json
{
  "aridCalls": ["Analytics", "CrashReporter", "sendEvent"],
  "disabledOperators": ["normalization-removal"],
  "enabledOperators": ["arithmetic"],
  "maxSwitchesPerExpression": 12,
  "exclude": ["Sources/Generated/**", "fastlane", "!Sources/Generated/Handwritten.swift"],
  "excludeDeclarations": ["*ForTesting", "*ForPreview"]
}
```

| Key | Meaning |
|-----|---------|
| `aridCalls` | Calls to leave alone. A call matches when the text of the called expression equals a pattern, starts with `<pattern>.` or `<pattern>(`, or its last name (method or function name) equals the pattern. A matching call is not removed as a statement and nothing inside its arguments is mutated. Use it for calls that tests do not and should not assert, such as analytics and crash reporting. Default: empty. The built-in list (`print`, `debugPrint`, `dump`, `NSLog`, `os_log`, `assert`, `assertionFailure`, `precondition`, `preconditionFailure`, `fatalError`, and the logging methods of `Logger`-like types) always applies |
| `disabledOperators` | Operators not to use. Names are in [operators.md](operators.md) |
| `enabledOperators` | Operators that are off by default and should be used |
| `maxSwitchesPerExpression` | How many mutants one expression may carry. Default 12 |
| `exclude` | File patterns to exclude; see below |
| `excludeDeclarations` | Names of declarations whose bodies are not mutated. A pattern is compared with the name (without the parameter list) of every declaration that encloses a candidate: the function, the property, the type. `*` stands for any text; without `*` the whole name must be equal. Candidates left out are listed as ignored with the reason `excluded-declaration`. Default: empty; see below |

- An unknown key is not ignored silently: it raises a warning on stderr and in the report (`warnings`, kind `config`). A typo should not quietly do nothing.
- A file that is not valid JSON, or a value of the wrong type, stops the tool with a message naming the file and the key.
- The command-line options `--arid`, `--disable-operator`, `--enable-operator` and `--exclude` add to the file's values.

Code that exists for the tests (`excludeDeclarations`). Product code often carries helpers that only the tests call, usually inside `#if DEBUG`: `resetForTesting()`, `_setClockForTesting(_:)`, `makeStubForPreview()`. Tests call them to prepare a state, not to check it. Their mutants are reached and then survive, or change nothing that a test looks at, so they add noise to a report.

Such helpers are not excluded by default, for two reasons. Which names mean "only for the tests" is a convention of each project (`reset…` is also the name of real features). And `#if DEBUG` alone says nothing: debug-only *behavior* deserves tests like any other. Name your convention once:

```json
{ "excludeDeclarations": ["*ForTesting", "*ForTests", "*ForPreview"] }
```

A pattern can also name a type (`"DebugMenu*"`): everything declared inside it is left out. To leave out a single declaration without a naming convention, put `// xcmutate:disable` … `// xcmutate:enable` around it.

## Which files are mutated

When files are given as arguments, exactly those are mutated and the rules below are not used.

Otherwise the candidates are the Swift files that git tracks, plus untracked files that are not ignored, minus:

| Reason (as shown in the report's `excluded`) | Files |
|----------------------------------------------|-------|
| `test-code` | Files that import a test framework: `import XCTest`, `Testing`, `Quick`, `Nimble`, or any `@testable import`. Import declarations count, not text: product code that holds the text of a test file in a string is not test code |
| `test-directory` | Files in a directory named like a test target (`Tests`, `…Tests`) that contains at least one `test-code` file: mocks and helpers |
| `generated-code` | Files whose first 15 lines have a comment marking generated code: `DO NOT EDIT`, `@generated`, `Generated by`, `Generated using`, `Code generated`, `auto-generated`, `autogenerated`, `automatically generated` (case-insensitive) |
| `package-manifest` | `Package.swift` |
| `build-or-dependency-directory` | Anything under `.build`, `DerivedData`, `.swiftpm`, `Pods`, `Carthage` |
| `fixtures-directory` | Anything under `Fixtures` |
| `config-exclude` | Matches of `exclude` in the config file or of `--exclude` |

- Names alone exclude nothing. `ABTest.swift`, or product code in a directory called `SplitTests/` that holds no tests, is mutated.
- `swiftlint:disable all` alone does not mark a file as generated; hand-written files carry it too.
- Nothing is dropped silently. The report's `excluded` lists a count per reason and the files. Test files in a directory named like a test target are counted and not listed one by one; a `test-code` file anywhere else is listed and named in a warning (`excludedTestCode`), because it may be product code. With `--since`, only files in the diff are listed, and a changed file that was excluded and is listed raises the warning `excludedChangedFile`.
- `--since` reads git's diff, whatever your git settings. `diff.mnemonicPrefix`, `diff.noprefix`, `core.quotePath` (paths with non-ASCII characters), external diff drivers and `*.swift -diff` in `.gitattributes` do not change what is selected. A file whose changes git hides (`git update-index --assume-unchanged` / `--skip-worktree`) counts as changed in every line when its text differs from the base, with the warning `sinceWholeFile`, because the work copy holds the changed text. When Swift files changed and none is mutated, a warning says which and why (`sinceNothingMutated`).
- `exclude` patterns use gitignore syntax: `*` and `?` do not cross `/`, `**` does; a pattern without `/` matches a name at any depth; a pattern that matches a directory covers everything below it. Patterns are applied in order after the default rules and the last match wins. A leading `!` re-includes a file, including one that a default rule excluded.

## Disable comments

| Comment | Scope |
|---------|-------|
| `// xcmutate:disable-next-line [operators…]` | The next line |
| `// xcmutate:disable-line [operators…]` | The same line |
| `// xcmutate:disable [operators…]` … `// xcmutate:enable [operators…]` | The lines in between, both ends included |

- With operator names (separated by spaces or commas) only those operators are disabled; without names, all are.
- A reason goes after ` -- `: `// xcmutate:disable-next-line boundary -- the boundary is covered by an integration test`.
- An unknown operator name is a warning and that directive disables nothing. With a typo such as `boundry`, hiding nothing and warning is the visible failure; hiding everything would not be. The warning appears on stderr and in the report (`warnings`, kind `disableComment`).
- The line that counts is the first line of the part that is rewritten. For `empty-body` that is the line of the function's `{`.
- Disabled candidates are listed as ignored with the reason `disabled-by-comment`.

## xcmutate.accepted.json

Written by `xcmutate accept` and read by `run` from `--root` (or `--accepted <path>`). It lists mutants accepted as equivalent, each with its stable key, the reason, the location and the date, and records the scheme of the keys (`keyVersion`, currently 2). Commit it and review changes to it like code. See [usage.md](usage.md#accept).

## The work directory

`run` keeps everything it produces outside your repository, in `--work-dir`. The default is `~/Library/Caches/xcmutate/<hash of root>.noindex` (the `.noindex` suffix keeps Spotlight away).

| Path | Content |
|------|---------|
| `src/` | The work copy |
| `DerivedData/` | Build products (and `SourcePackages`) |
| `journal/observations.jsonl` | One line per finished mutant, used by `--resume` |
| `report/` | Default location of the `json`, `markdown`, `html` and `stryker` reports |
| logs and result bundles | Build and test logs; per-mutant `.xcresult` bundles are removed unless `--keep-results` is given |
| `xcmutate-workdir.json` | Marker: tool, version, root and time of last use |
| `xcmutate.lock` | Held by the run that uses the directory |

`run` deletes `src/`, `logs/`, `results/` and `traces/` at its start. It therefore refuses, before deleting anything (exit code 2), a `--work-dir` that

- exists, is not empty and was not made by the tool (no marker file, and not under `~/Library/Caches/xcmutate`);
- is `--root`, the repository that holds it, or a directory above them; the home directory or a directory above it; or `/`;
- is inside the tree that is copied without being ignored by git (the copy would contain the work directory). A directory under `.build/` is fine.

Two runs cannot use one work directory at the same time: the second stops with exit code 2 and names the first. Remove work directories with `xcmutate clean` ([usage.md](usage.md#clean)).

## Environment variables

| Variable | Set by | Read by |
|----------|--------|---------|
| `XCMUTATE_ACTIVE` | `run`, as `TEST_RUNNER_XCMUTATE_ACTIVE_<token>` in the environment of `xcodebuild`, which strips the prefix | The embedded helper: the id of the mutant to switch on |
| `XCMUTATE_TRACE` | `run` | The helper: the file to append reach and activation records to |
| `XCMUTATE_TRACE_TESTS` | `run`, during the baseline of `--select-tests reach` | The helper: record reach per test |
| `XCMUTATE_ORIGINAL_ROOT` | `run` | Your `--prepare` command: the original `--root` |
| `XCODEGEN` | you | The repository's own `scripts/*.sh` only: path of the `xcodegen` executable |

You normally set none of the first three yourself; they matter when you drive an instrumented build by hand ([how-it-works.md](how-it-works.md)).

**The token.** In a build made by `run`, the names of the first three (and of `XCMUTATE_SHARED`, used by `--shared-process`) end in a token that is derived from the work directory: `XCMUTATE_ACTIVE_1K2J3H…`. A test process hands its environment to the processes it starts. A child built from the same embedding (your product's own executable, started by a test) reads the same names and has the same mutant on, as it must. A child that holds another embedding (a program that a test instruments and compiles itself, another checkout's build) reads other names and is not affected: without the token, the mutant with the same number would be switched on in it. Files written by `instrument` use the plain names.
